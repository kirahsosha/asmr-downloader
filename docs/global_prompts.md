## 3. 提交策略约束

### 3.1 禁止主动提交

- 除非用户提示词中**明确说明**需要提交改动，否则**禁止**创建或推送 commit。
- 在未收到明确请求时，**仅允许**修改文件和添加待提交记录。

### 3.2 提交执行流程

当用户明确要求提交时，按以下顺序执行：

1. **前置检查**：执行全量回归测试（`dotnet/tests/` 下所有测试项目），结果必须全部通过。如果测试失败，提示用户并停止执行，**禁止**直接进入修复作业。
2. **文件内容检查**：不进行任何文件内容检查以及修改文件内容，直接按照当前状态提交。所有非AI提交的变更默认是用户的合理修改。
3. **暂存**：`git add .`（默认提交工作区**全部改动**，除非用户明确指定范围）。
4. **提交**：`git commit -m "<Summary>" -m "<Description>"`
   - Summary 和 Description 必须来自章节 3.1 中状态为 `待提交` 的记录。
   - Description 中的 `<br>` 必须替换为实际换行，删除空行，确保每个序号独占一行。
   - 若遇到序号错误，**必须**修正序号。
   - 从输出中记录 7 位短 SHA（如 `0b7644c`）。
5. **回填**：提交成功后立即更新章节 3.1：
   - `状态`：`待提交` → `已提交`
   - `Commit SHA`：`-` → 实际 7 位短 SHA
   - 回填改动本身**不做单独 commit**（见 §3.3），自然并入下一次代码提交。

### 3.3 禁止单独提交明细

如果唯一的改动是 `docs/wpf-migration-progress.md` 中章节 3.1 的提交明细更新，**禁止**将其作为独立提交；**必须**与后续的代码改动一同提交。

## 6. 代码审查约束

用途：用 Copilot 流程审查任意代码（例如 Pull Request）。严格按下列步骤执行，不得更改语义或约束。

### 步骤

1. 资格检查（轻量）：确认代码/PR 不是已关闭、草稿、不需审查（如自动 PR、极小改动）、或已由你审查；若任一成立则停止。

2. 列出相关提示文件路径（只列路径，不读内容）：返回仓库根及受影响目录中相关的提示/CLAUDE.md 等文件路径。

3. 概要：读取变更并返回简短摘要。

4. 并行启动 5 个审查器（每个返回问题列表并说明标记理由，如提示文件依从性、bug、历史上下文等）：
   - 审查器#1：对照提示文件做合规性审计（仅指出提示文件明确要求的项）。
   - 审查器#2：仅看变更内容，浅层扫描明显缺陷，重点重要问题，避免琐碎 nitpick。
   - 审查器#3：查看 git blame/历史以判断历史相关风险。
   - 审查器#4：查阅此前触及这些文件的 PR 与 review 评论，找可复用结论。
   - 审查器#5：检查代码注释中对变更的指导是否被遵守。

5. 对步骤4中每个问题进行置信度评分（0／25／50／75／100），定义如下：
   - 0：完全不确信（误报或先前存在）。
   - 25：部分确信（可能为真，但无法验证；或为风格问题且提示文件未明确）。
   - 50：中等确信（真实但次要）。
   - 75：高度确信（复核后很可能影响功能，或提示文件明确指出）。
   - 100：绝对确定（证据充分，必然发生）。
   - 说明：若问题因提示文件被标记，须核对提示文件文本以确认指示确实存在。

6. 过滤：剔除置信度小于 60 的问题；若无剩余问题则停止（不继续）。

7. 再次做第1步的资格检查，确认仍可审查。

8. 必要时使用 `gh` CLI 在 PR 上发表评论（遵守仓库全局 CLI 规则，例如通过 `rtk` 执行）。发表评论要求：保持简洁、避免 emoji；为每个问题提供链接并引用相关文件/代码/URL；链接必须使用完整 git SHA 且包含行号范围，至少提供前后各一行上下文（行范围格式 L[start]-L[end]）。

9. 生成审查报告。

### 误报示例（不作为问题）

- 先前已存在的问题
- 看似 bug 但非 bug
- 资深工程师不会提出的啰嗦 nitpick
- 可由 linter/typechecker/CI 捕获的问题（格式、导入、类型错误等）
- 普通代码质量建议（除非提示文件要求）
- 提示文件明确被忽略的情况（如 lint ignore）
- 与变更意图一致的功能改动
- 变更未修改行上的问题

注意：

- 不要尝试构建或 typecheck（CI 会执行）。
- 使用 `gh` 交互时请遵守全局 CLI 要求（例如通过 `rtk`）。
- 审查前请先建立 todo list 并按其执行。
- 报告中必须为每个问题提供可点开的引用链接并说明理由。
